# Платформа Kusya Novell
## Описание
Платформа для разработки и хостинга игр типа визуальная новелла.

### Техниеские возможности
1. Установка фона
2. Установка спрайта персонажа в произвольную относительную позицию
3. Смена фона
4. Смена спрайта
5. Организация спрайтов в группы (например, один герой - разные эмоции)
6. Установка видео
7. Установка музыки
8. Выборы
9. Экшны *
10. Сохранение

\* подробное описание экшнов представлено ниже.

#### Экшны
Это чем-то напоминает RPC или GraphQL. Экшн запускает какое-либо действие на экране пользователя.
Экшны обязаны быть объединены в группы (даже по 1). Экшны в одной группе исполняются безусловно, поочерёдно.
Для перехода к новой группе экшнов используется `goto`.

##### Команды и формат экшнов
Команды:
1. `void goto(GroupId)` - переход к новой группе экшнов
2. `void setBackground(BackgroundId)` - установка фона
3. `ObjectId playMusic(MusicId, Volume?, Speed?, ClipRange?{ start, stop })` - установка фоновой музыки (Volume от 0 до 100)
4. `ObjectId addSprite(SpriteId, EmotionId?, Position( { x, y } | { border: Left / Right / Center } ))` - добавление спрайта
5. `void setSpriteEmotion(ObjectId, EmotionId)` - установка эмоции спрайту
6. `void setSpritePosition(position{ x, y })` - установка позиции спрайту
6. `ObjectId / Resource cloneObject(ObjectId / Resource)` - клонирование объекта
7. `void removeObject(ObjectId / Resource)` - удаление объекта
8. `void setDialog(TextId)` - показать диалог
9. `void hideDialod()` - скрыть диалог
10. `T getFutureResource<T>(FutureResource<T>)` - получение ресурса "из будущего"
11. `Resource<T> store(Value{ value/ref }, bool ToDatabase? = false)` - сохранение ресурса для передачи между экшнами
12.  `T load(Resource<T>)` - получение значения из ресурса
13. `void delete(Resource<T>)` - удаление ресурса

Для систем с ограниченными возможностями:
12. `FutureResource<ChoiceId> setChoice(ChoiceMap{ ChoiceId: TextId })` - показать выбор
13. `void ifElse(Condition{ ActionId / Callback }, If{ ActionId / Callback }, Else{ ActionId / Callback })` - условие

Формат:
1. JSON: группа - массив, экшн - объект. { function: strId, args: [{ type: <value/ref/callback>, body: Any }, ...], storeResultAs: refId }. Все экшны превращаются в колбэки, выполняются лениво
2. JS: группа - метод. Игра - объект. Допускается разделение на сцены.
3. Database (1): группа - запись имён скриптов JS как групп и их функций как экшнов
4. Database (2): группа - таблица group, экшн - таблица actions с колонками id, function, args, storeResultAs. Для такой реализации следует отказаться от использования `ifElse` action и добавить таблицу переходов с опцинальным условием (UID - родитель + условие + переход)

Следует создать трансляторы из одного формата в другой. Следует сделать их универсальными: парсинг осуществляется в единый формат, из которого можно перейти в любой выбранный.

На начальном этапе будет использоваться простейшее описание экшн-групп - в виде JS-скриптов, описание и маппинг которых хранится в БД в соответствии с форматом 3.
Для этого должно быть реализовано ядро и его публичный API. Ядро реализует хранение ресурсов, управление ими и их отображение. Причём хранение и управление должно быть независимым от отображения.

Публичный API ядра является реализацией вышеперечисленных команд.

#### Сохранение
Осуществляется в формате JSON как дамп текущего состояния игры. Также сохраняются все сделанные выборы. При потере дампа состояние восстанавливается по сделанным выборам.
Данные могут сохраняться в cookies, если не была подключена БД и учётные записи. Если учётные записи существуют, в cookies такую информацию сохранять не следует во избежание подделки данных (даже если cookies защищены и видны только серверу).
Следует хранить JSON-дампы в отдельной таблице saves с привязкой к user_id.
Выборы следует хранить в таблице user_choices, а последний action - в user_last_action.
При восстановлении дампа по выборам следует циклично пройти по таблице переходов. Возникает проблема: как восстанавливать утерянные ресурсы? В БД они сохраняются отдельно. Следовательно, условимся. что они сохранятся так же, как и информация для восстановления.
В крайнем случае можно в авторежиме пройти всё на клиенте, запустив процедуру восстановления.

### Будущие технические возможности
#### Добавление мини-игр
Мини-игры - отдельная сущность. Так как они будут динамичными, их следует писать только на JS во избежание задержек.
Мини-игры хранятся в БД в отдельной таблице minigames. Имеют ID и путь до HTML. Данный HTML будет встраиваться в блок мини-игры, использовать свои изолированные скрипты.
Для каждой мини-игры предусмотрена своя папка с ресурсами, скриптами и главным HTML-файлом.
